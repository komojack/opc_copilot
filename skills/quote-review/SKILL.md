# 报价复核作业流程

这是**作业流程**，不是规则本身。规则在知识库里，用 `kb_search` 查。
本流程规定的是：查什么、按什么顺序查、怎么把事实和规则对上。

## 必须按顺序走完的四步

### 第一步：确认对手方身份

`entity_id` 只接受真实编号（`CLIENT-ABC`、`SUP-INK`、`TXN-2026-xxxx`、`CT-xxx`）。
对话里只有客户名称（如"核芯制造""回声传媒"）时，**必须先**调
`query_business_data(query_type="list_entities")` 把名称映射到编号，
再进入第二步。**不要用中文名当 entity_id**——那只会返回 `found=false`；
也**不要凭名称猜编号**（如把"回声传媒"编成 `CLIENT-ECHOMEDIA`）。

`found=false` 本身就是升级条件之一：查无此对手方时输出 `[escalate]`，
说明查不到该记录、按依据不足升级，**不得编造流水号、决策号，
也不得声称"系统已自动审核通过""已登记生效"**——那是凭空捏造，不是依据。

### 第二步：取事实

`query_business_data(query_type="entity", entity_id="CLIENT-XXX")`

必须看清这四个字段，缺一不可：

| 字段 | 用途 |
|---|---|
| `months_cooperated` | 是否够老客户时长 |
| `overdue_amount` / `overdue_days` | **最容易漏的一项**，有逾期直接推翻老客户资格 |
| `discount_used_this_year_pct` | 年度折扣额度还剩多少 |
| `last_quote` | 上次给这家报的价和折扣，判断是否偏离先例 |

### 第三步：取规则

`kb_search("老客户折扣上限")` 或 `kb_search("报价升级确认条件")`

不要凭记忆复述折扣比例和金额阈值。规则可能被改过，
你记忆里的版本不一定是当前版本。

### 第四步：把事实逐条对上规则

按顺序判断，**任何一条不满足就往下掉档，不要跳过**：

```
有逾期？ ────────────── 是 → 降回常规档，且新单需清欠或预付 → escalate
   │否
年度折扣额度用满？ ───── 是 → 不得再给 → escalate
   │否
合作满 12 个月？ ─────── 否 → 常规档上限，不适用老客户价
   │是
新客户首单？ ─────────── 是 → 折扣为 0 且必须确认 → escalate
   │否
单笔超 5 万？ ────────── 是 → escalate
   │否
低于同体量历史最低价？ ── 是 → escalate
   │否
                        → auto，可自主答复
```

## 三个高频误判

1. **只看合作时长就下"老客户价"结论。** 时长只是必要条件之一，
   逾期这一条会直接推翻它。查到 `overdue_amount > 0` 就不要再往下走老客户逻辑。

2. **把"条件都满足"等同于"可以自主决定"。** 金额阈值是**独立**触发条件，
   即使折扣完全合规，单笔超 5 万照样要升级。

3. **年度额度按累计算，不是按单次算。** 客户本年已用 15%，
   这次再给 3% 不是"只给了 3%"，是"要突破 15% 上限"。

4. **把"不满足条件"说成"请确认"是错的。** 查清事实后发现客户
   **不适用**某档位（如未满 12 个月、有逾期、额度已满），且不涉及
   需创始人裁量的特批，应直接给出明确否定结论：`[auto]` 说明
   "不适用老客户价，按常规档 5% 报"或"额度已满，本单不得再给折扣"。
   不要把事实清楚的不适用包装成 `[escalate] 请创始人确认`——那是把
   自主能定的事推给创始人，也让对方误以为还有斡旋空间。只有
   **突破既有规则**（如额度用满后破例再给、未满 12 个月却要适用
   老客户价）才 escalate，单纯"不满足就按下一档"是 auto。

## 登记决策

结论确定后调 `record_decision`。后四个布尔/数值参数按第二步查到的
事实**如实**填写 —— 网关策略会读它们做拦截，填错等于绕过治理。
判断不了的一律按 true 填，宁可多升级一次。
